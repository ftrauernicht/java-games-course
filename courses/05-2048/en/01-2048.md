# Course 5 – 2048

**Goal:** the sliding tile game. Four directions that are really one operation
applied to a turned board, and a merging rule that almost everybody gets wrong on
the first attempt.

![A board in a window: 4, 2, 8, 2 along the top row, then 16, 8 and 2, and a red 64 tile at the left of the third row](../assets/gameplay.png)

The board lives in a window, the move is still typed and confirmed with Enter.
That split is deliberate, and it is the argument for Course 6: a window can show
anything, but reading a single key the moment it is pressed takes more than this.

Assumes [Course 1](../../01-basics/en/00-introduction.md) and nothing else. A
finished version lives in [`code/Game2048.java`](../code/Game2048.java).

## 🟢 Core — The game, and the name of the class

A four by four board. Every move slides every tile as far as it goes in one
direction. Two tiles with the same number that run into each other merge into one
tile of twice the value. After every move that changed something, a new tile
appears on a free square.

Start the file. It cannot be called `2048.java`, because a Java name may not begin
with a digit, so the class is `Game2048` and the file is `Game2048.java`:

```java
import java.util.Scanner;

public class Game2048 {

    static final int SIZE = 4;

    public static void main(String[] args) {
    }
}
```

`static final int SIZE = 4;` sits inside the class and outside every method. That
is new: Course 1 shows `final` only on a variable **inside** a method, where it ends
with the method. Here the number belongs to the class, and every method can reach
it — which is exactly what you need in a moment, because `draw`, `move` and `spawn`
all use it.

## 🟢 Core — Two-dimensional arrays, in short

*(If you have done Course 2 or Course 4, skip ahead to the next section.)*

Course 1 gave you an array: a row of values under one name. A board is an array
whose values are themselves arrays:

```java
int[][] board = new int[SIZE][SIZE];
```

`board[1][2]` is row 1, column 2, and both count from 0. The type is `int` because
a square holds a number, and a fresh `int` array is full of zeros, so 0 can stand
for an empty square without any setting up.

Walking the whole board is a loop inside a loop:

```java
for (int row = 0; row < SIZE; row++) {
    for (int col = 0; col < SIZE; col++) {
        // board[row][col]
    }
}
```

One more thing this chapter uses: `board[row]` on its own, without a second pair
of brackets, is the whole row, and it is an `int[]`. A board is really an array of
rows, so a method that works on one row can be handed `board[2]` directly.

It works the other way round too, and both key moments in this chapter depend on
it: `board[row] = someOtherRow` replaces that whole row in one go. Course 1 said an
array variable holds the location of its values rather than the values themselves,
and this is that fact doing something useful.

## 🟢 Core — A board in a window, whose numbers grow

*(Course 4 uses the same window. If you came from there, skip to the next
section.)*

A window costs seven lines here and no class of your own. Nothing is overridden,
nobody listens for anything; that only arrives in Course 6, and because of the
keyboard rather than the display.

Three things are needed: a `BufferedImage` as a picture in memory that you paint
on, a `JLabel` you can hand a picture to, and a `JFrame` as the frame around it.

```java
import java.awt.Color;
import java.awt.Font;
import java.awt.FontMetrics;
import java.awt.Graphics;
import java.awt.image.BufferedImage;
import javax.swing.ImageIcon;
import javax.swing.JFrame;
import javax.swing.JLabel;
```

First the measurements and the colours, up with the other constants in the class.
The window lines below use `BOARD`, so it has to be there already:

```java
static final int TILE = 90;
static final int GAP = 8;
static final int BOARD = SIZE * TILE + (SIZE + 1) * GAP;

static final Color BACKDROP = new Color(187, 173, 160);
static final Color EMPTY = new Color(205, 193, 180);
static final Color DARK_TEXT = new Color(119, 110, 101);
```

Four tiles of 90 pixels and five gaps of 8 make 400. `BOARD` works itself out from
the other two rather than writing the 400 down a second time somewhere: set `TILE`
to 60 and window, tiles and gaps still agree with each other.

`new Color(187, 173, 160)` is red, green and blue from 0 to 255. This is the first
time in this course that `new` builds something that is not an array; there is
nothing more to it than the class `Color` taking three numbers and making a colour
object out of them.

Now the window, eight lines in `main`:

```java
BufferedImage picture = new BufferedImage(BOARD, BOARD, BufferedImage.TYPE_INT_RGB);
JLabel label = new JLabel(new ImageIcon(picture));
JFrame window = new JFrame("2048");
window.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
window.add(label);
window.pack();
window.setLocationRelativeTo(null);
window.setVisible(true);
```

Line by line, because six names turn up here at once:

`new BufferedImage(width, height, TYPE_INT_RGB)` makes a picture that size.
`TYPE_INT_RGB` is a constant of the class and means "red, green and blue per pixel,
no transparency". For a board that is the right choice.

A `JLabel` shows either text or a picture. It does not take a `BufferedImage`
directly, though; an `ImageIcon` belongs in between, and it does nothing but wrap a
picture in the form Swing expects. Hence the nesting.

`setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE)` says what the close button should
do: end the whole program. Without that line only the window goes away and the
program carries on — remember that, it comes up again further down, and there it
costs you a quarter of an hour otherwise.

`add` puts the label in the window, `pack()` lays the window around its contents
instead of leaving you to guess a size, `setLocationRelativeTo(null)` centres it on
the screen, and `setVisible(true)` shows it. Before that last line you see nothing.

You draw with `Graphics`, which you get from the picture:

```java
static void draw(BufferedImage picture, int[][] board) {
    Graphics g = picture.createGraphics();

    g.setColor(BACKDROP);
    g.fillRect(0, 0, BOARD, BOARD);

    for (int row = 0; row < SIZE; row++) {
        for (int col = 0; col < SIZE; col++) {
            int x = GAP + col * (TILE + GAP);
            int y = GAP + row * (TILE + GAP);
            int value = board[row][col];

            g.setColor(value == 0 ? EMPTY : tileColor(value));
            g.fillRect(x, y, TILE, TILE);

            if (value != 0) {
                drawNumber(g, value, x, y);
            }
        }
    }
}
```

Row and column become pixels through `GAP + col * (TILE + GAP)`: one gap at the
edge, then each tile's width plus the gap behind it.

One more line belongs at the very end of `draw`:

```java
g.dispose();
```

`createGraphics()` hands you a new tool every time, and `dispose()` gives it back.
With one picture that is of no consequence, over a few hundred moves it is. One
line, and you do not have to know when it starts to hurt.

The colour follows the value. A `switch` makes that choice, but not the way Course
1 showed it: there `switch` was a **statement**, here it is a **value** sitting
behind `return`. Every branch yields something, and together they are the result of
the method — which is why there is a semicolon after the closing brace, where a
statement would have none:

```java
static Color tileColor(int value) {
    return switch (value) {
        case 2 -> new Color(238, 228, 218);
        case 4 -> new Color(237, 224, 200);
        case 8 -> new Color(242, 177, 121);
        case 16 -> new Color(245, 149, 99);
        case 32 -> new Color(246, 124, 95);
        case 64 -> new Color(246, 94, 59);
        default -> new Color(237, 194, 46);
    };
}
```

Pale for small tiles, hot for large ones. That is not decoration: it shows you how
far along you are without reading a single number.

The fixed-column-width problem a text version would have does not exist in a
window. It has one of its own instead: a `1024` is more than twice as wide as a `2`
and runs off the edge at a fixed font size. So the font shrinks as the digits grow,
and the number is centred on its tile:

```java
static void drawNumber(Graphics g, int value, int x, int y) {
    String text = String.valueOf(value);

    int size = switch (text.length()) {
        case 1, 2 -> 38;
        case 3 -> 32;
        default -> 26;
    };

    g.setFont(new Font("SansSerif", Font.BOLD, size));
    g.setColor(value <= 4 ? DARK_TEXT : Color.WHITE);

    FontMetrics metrics = g.getFontMetrics();
    int textX = x + (TILE - metrics.stringWidth(text)) / 2;
    int textY = y + (TILE + metrics.getAscent() - metrics.getDescent()) / 2;
    g.drawString(text, textX, textY);
}
```

Three small things in that piece are new. `String.valueOf(value)` turns a number
into text; `"" + value` from Course 1 would do the same and reads worse.
`case 1, 2 ->` folds two cases into one branch, which arrow `switch` allows. And
`new Font("SansSerif", Font.BOLD, size)` is font name, style (`Font.PLAIN`,
`Font.BOLD`, `Font.ITALIC`) and size in points.

`FontMetrics` answers questions about the font currently set. `stringWidth` is the
width of this text in pixels; half of what is left over, placed to its left, centres
it horizontally.

Vertically it is trickier, because `drawString` sets the **baseline** and not the
top edge. `getAscent` is how far the font reaches above the baseline, `getDescent`
how far below.

Try `textY = y + TILE / 2`, putting the baseline exactly on the middle. The numbers
then sit visibly **too high**. Measured on a 90-pixel tile at font size 38: the ink
runs from y=18 to y=44, so its middle lands at 31 rather than at 45 — fourteen
pixels out, and you see it at once.

The formula above moves the baseline down by half the difference between ascent and
descent. The ink then runs from y=33 to y=59, middle 46 against 45: **one pixel too
low**, and nobody sees that.

It is still not exact, and the reason is instructive. It centres not the digit but
the space the font *could* occupy — ascent 39 plus descent 9. A digit uses neither
the descender nor the full ascent; measured, it is 27 pixels tall and not 39. Two
inaccuracies that very nearly cancel. If that one pixel bothers you, measure the
real extent of this text with `metrics.getStringBounds(text, g)`.

One more line, the one people forget:

```java
label.repaint();
```

Painting into the picture changes nothing on screen. Only `repaint()` puts it there.
So: draw, then `repaint`, then ask for the move.

A new tile goes on a random free square, and is usually a 2:

```java
static void spawn(int[][] board) {
    while (true) {
        int row = (int) (Math.random() * SIZE);
        int col = (int) (Math.random() * SIZE);
        if (board[row][col] == 0) {
            board[row][col] = Math.random() < 0.9 ? 2 : 4;
            return;
        }
    }
}
```

Guessing until the guess lands on a free square is fine while the board is mostly
empty, and this one is never called on a full board.

Put two tiles down and print:

```java
int[][] board = new int[SIZE][SIZE];
spawn(board);
spawn(board);

draw(picture, board);
label.repaint();
```

## 🟢 Core — Typing a move, and the Enter key in the way

In the real game you press an arrow key and the board moves at once. Here you will
type a letter and press Enter, and that is not a shortcut. Java cannot read a
single keypress from a terminal at all. The terminal collects a whole line before
handing anything over, and the JDK has no way to ask it to stop doing that. Arrow
keys are worse: they arrive as several characters at once.

So: `w`, `a`, `s`, `d`, and `q` to quit, each followed by Enter.

```java
Scanner in = new Scanner(System.in);

System.out.print("Move (w/a/s/d, q to quit): ");
String line = in.nextLine().trim().toLowerCase();
```

`.toLowerCase()` means a stray capital `W` still works, and `.trim()` forgives a
space.

Handle the quit key before anything else, because it is not a direction and has no
business going through the direction lookup:

```java
if ("q".equals(line)) {
    System.out.println("Bye.");
    System.exit(0);
}
```

That says `System.exit(0)` and not `return`, and it is the nastiest surprise in
this chapter. For as long as a window is open, Swing keeps a thread of its own
alive, and it is not a background thread. Returning from `main` therefore does
**not** end the program: `Bye.` appears, the prompt never comes back, and the
terminal hangs until you kill it. Try it with `return` once so that you have seen
the behaviour; anybody who does not know it looks for the fault in their own code.

`System.exit(0)` ends the whole JVM at once. The zero means "no error". The same
applies at game over further down. The third way out is the window's close button,
and that works only because `setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE)` is up
there.

The board now looks like a game, and you still steer it with Enter. That
contradiction is exactly the limit Courses 6 and 7 escape, by letting the window
take the key itself rather than only show things. It is worth knowing which of the
two is the real constraint: the terminal, not Java's ability to make games.

## 🟢 Core exercise — Sliding one row

Everything in this game happens to a single row, moved to the left. Get that right
and the rest is bookkeeping.

```java
static int[] slideRowLeft(int[] row) {
    // your code here -- the three steps below
}
```

1. **Compact.** Walk the row and copy every non-zero value into a new array, one
   after another from position 0. Gaps disappear; order stays.
2. **Merge.** Walk the compacted array from left to right, stopping one short of
   the end, because each step looks at the value next to it as well. Whenever a
   value is not 0 and equals the one beside it, double the first and set the
   second to 0.
3. **Compact again.** Merging leaves holes, so do step 1 once more and return the
   result.

Step 2 stops at `SIZE - 1` and not at `SIZE`. The loop reads `packed[i + 1]`, so
running all the way to the end reaches one past the array.

What happens then depends on the contents, and that is what makes the bug mean.
With `2 4 2 4` it blows up at once:
`ArrayIndexOutOfBoundsException: Index 4 out of bounds for length 4`. With
`2 2 2 2` — the first test row right below — it does **not**, because `packed[i]
!= 0` sits to the left of the `&&` and is already false at the last position, so
`packed[4]` is never read. The result is then quietly `4 . 4 .` instead of
`4 4 . .`.

A bug that sometimes crashes and sometimes returns a wrong answer is worse than one
that always crashes. So set the bound right from the start rather than trusting that
it will show up.

A tile may merge at most once per move, and in this version the test for 0 is what
enforces that: a merged partner becomes 0, so the next step cannot pick it up
again. That is worth knowing because it is easy to assume some extra bookkeeping
is needed and then write it.

Work these out on paper before you write anything:

```
2 2 2 2   becomes   4 4 . .      (two separate merges, not one 8)
4 2 2 .   becomes   4 4 . .      (the two 2s merge; the 4 is untouched)
2 2 4 .   becomes   4 4 . .      (same result, different reason)
4 4 4 4   becomes   8 8 . .
2 4 2 4   becomes   2 4 2 4      (nothing merges, nothing moves)
```

The third line is the one that decides whether your version is right, and the
reason is worth meeting head-on.

Three steps with a separate array look like more work than they need to be, and
the tempting shortcut is to build the result in one pass: keep a write position,
and for each incoming value either start a new tile or double the one you just
wrote. It is shorter and it is wrong. On `2 2 4 .` it merges the two 2s into a 4,
then meets the existing 4 next to the 4 it has just written, and merges again:
`8 . . .`. The tile it created in this move merges a second time in the same move.

Compact, merge, compact avoids that because the merging pass only ever looks at
values that were already there when the pass started. The cost is one extra array
and one extra walk; the benefit is a rule that cannot be broken by accident.

Test your method on all five rows above before going near the board.

## 🟢 Core — Four directions, one operation

You now have "left". Rather than writing three more versions, turn the board and
use the one you have.

```java
static void rotateClockwise(int[][] board) {
    int[][] turned = new int[SIZE][SIZE];
    for (int row = 0; row < SIZE; row++) {
        for (int col = 0; col < SIZE; col++) {
            turned[col][SIZE - 1 - row] = board[row][col];
        }
    }
    for (int row = 0; row < SIZE; row++) {
        board[row] = turned[row];
    }
}
```

The square at `(row, col)` lands at `(col, SIZE - 1 - row)`. Take a piece of paper
with a letter in each corner and turn it a quarter turn to convince yourself.

The last loop copies the rows back into the board that was handed in, so the caller
sees the change. Assigning `board = turned` would only point the local name at the
new one and change nothing outside, which is the limit of what "arrays are
references" buys you.

Then a move is: turn, slide every row left, turn back.

```java
static void move(int[][] board, int rotations) {
    for (int i = 0; i < rotations; i++) {
        rotateClockwise(board);
    }

    for (int row = 0; row < SIZE; row++) {
        board[row] = slideRowLeft(board[row]);
    }

    for (int i = 0; i < (4 - rotations) % 4; i++) {
        rotateClockwise(board);
    }
}
```

How many turns for which direction is worth deriving rather than memorising, but
here is the answer so you can check yourself: left is 0, down is 1, right is 2, up
is 3. Test each one with a single tile in a known corner and see where it ends up.

The `switch` from Course 1 turns a letter into that number:

```java
int rotations = switch (line) {
    case "a" -> 0;
    case "s" -> 1;
    case "d" -> 2;
    case "w" -> 3;
    default -> -1;
};

if (rotations < 0) {
    System.out.println("Type w, a, s or d, or q to quit.");
    continue;
}
```

This is a `switch` used as a value rather than as a statement: the whole thing
produces a number, which is why it ends with a semicolon. `-1` stands for "not a
direction", in the same way Course 2 used 0 for "no square".

## 🟢 Core — A move that changes nothing

Push everything left twice and the second push does nothing. If a new tile appears
anyway, the player gets free tiles for pressing a key that did not move anything,
and the board fills up with no game played.

So compare before and after:

```java
int[][] before = copy(board);
move(board, rotations);

if (same(before, board)) {
    System.out.println("Nothing moves that way.");
    continue;
}

spawn(board);
```

`copy` and `same` are both a loop inside a loop, one writing and one comparing:

```java
static int[][] copy(int[][] board) {
    int[][] result = new int[SIZE][SIZE];
    for (int row = 0; row < SIZE; row++) {
        for (int col = 0; col < SIZE; col++) {
            result[row][col] = board[row][col];
        }
    }
    return result;
}
```

Why not `int[][] before = board;`? Because that is one board with two names, and
after the move both names show the moved board. The comparison then always says
"nothing changed", so no tile ever appears and the game announces
"Nothing moves that way." after every single move, while the board visibly moves.
Course 1 warned about exactly this under "arrays are references", and this is the
place where forgetting it produces a game that looks broken in a way the code does
not explain.

Write `same` yourself; it is `copy` with a comparison instead of an assignment, and
an early `return false`.

Now the loop in `main`. It is the piece where everything comes together, so here is
its frame:

```java
while (true) {
    draw(picture, board);
    label.repaint();

    System.out.print("Move (w/a/s/d, q to quit): ");
    String line = in.nextLine().trim().toLowerCase();

    // your code here -- handle q, work out the direction, reject bad input,
    // copy the board, move, compare against the copy

    spawn(board);

    if (isFull(board)) {
        draw(picture, board);
        label.repaint();
        System.out.println("Board full. Game over.");
        System.exit(0);
    }
}
```

The order is not free. Drawing happens **before** asking for the move, otherwise you
are always looking at the board from last time but one. And `spawn` comes after the
comparison, because a move that changed nothing must not hand out a free tile.

`isFull` you still need: a double loop that returns `false` as soon as it finds a 0
and `true` otherwise. Three lines, the same shape as `same`.

Here too `System.exit(0)` and not `return`, for the same reason as with `q`.

## 🟡 Optional — A score

Add up the value of every merge and show the total. The only place a merge happens
is inside `slideRowLeft`, which returns a row and so has nowhere to put a second
answer.

The straightforward way needs something Course 1 did not show: a variable that
lives in the class rather than in a method, so that `slideRowLeft` and `main` can
both reach it.

```java
static int score;
```

Unlike `SIZE` it is not `final`, because it changes. Add to it where the merge
happens, print it next to the board, and reset it where a new game starts.

One interaction to watch for if you also do the red challenge below: a game-over
check that tries all four moves to see whether any of them does something would
run `slideRowLeft` for each trial and inflate the score. The neighbour test in that
section avoids the problem by not moving anything, which is one more reason to
prefer it.

## 🟡 Optional — Several moves on one line

One move per Enter gets tedious. Accept `wasd` as four moves in one line, by
looping over the characters with `charAt` from Course 1 and treating each as its
own move.

Mind the detail this exposes: after each letter you have to check whether the board
changed and whether to spawn, exactly as the single-move version does.

## 🔴 Optional, genuine challenge — Game over, properly

The green version ends when the board is full. That is not the real rule. A full
board is still playable if two equal tiles sit next to each other, because that
move merges them and frees a square.

Write the real check: the game is over when there is no empty square **and** no two
orthogonal neighbours are equal.

```java
static boolean isGameOver(int[][] board) {
    // your code here -- no empty square, and no equal neighbours
}
```

Comparing each square with the one to its right and the one below it is enough to
cover every neighbouring pair exactly once. Work out why checking left and up as
well would be wasted effort.

Then the second half, which is harder to resist getting wrong: a tile merging
freely in one direction may be blocked in another. Convince yourself that the
neighbour test above does not care about direction, and that this is correct.

Build a full board on purpose to test it, by filling the array by hand in `main`
before the loop starts.

## What you learned

- A board as `int[][]`, and `board[row]` as a whole row you can hand to a method
- A window that shows something: `BufferedImage` to paint on, `JLabel` to display
  it, `JFrame` as the frame, and `repaint()` as the line without which nothing
  happens
- Turning row and column into pixels, and deriving one measurement from the others
  instead of repeating it
- A `switch` that yields a colour, and why colour is information here
- `FontMetrics`, baseline against top edge, and why centred text is measured rather
  than guessed
- That a terminal cannot deliver a single keypress, and what that costs
- Compact, merge, compact, and why a tile may merge only once
- Turning a board so that one operation serves all four directions
- A `switch` used as a value rather than as a statement
- Copying a board rather than renaming it, and why the difference decides the game
- *(optional)* Checking every neighbouring pair exactly once
