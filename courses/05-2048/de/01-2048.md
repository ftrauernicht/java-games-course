# Kurs 5 – 2048

**Ziel:** das Schiebespiel. Vier Richtungen, die in Wirklichkeit eine einzige
Operation auf einem gedrehten Spielfeld sind, und eine Verschmelzungsregel, die
fast jeder im ersten Anlauf falsch macht.

![Ein Spielfeld im Fenster: 4, 2, 8, 2 in der obersten Reihe, darunter 16, 8 und 2, in der dritten Reihe links ein rotes 64er-Plättchen](../assets/gameplay.png)

Das Spielfeld steht im Fenster, der Zug wird weiter getippt und mit Enter
bestätigt. Diese Trennung ist Absicht und sie ist das Argument für Kurs 6: Zeigen
kann ein Fenster alles, aber eine einzelne Taste im Moment des Drucks zu lesen
braucht mehr als das hier.

Setzt [Kurs 1](../../01-basics/de/00-einfuehrung.md) voraus und sonst nichts. Eine
fertige Fassung liegt in [`code/Game2048.java`](../code/Game2048.java).

## 🟢 Kern — Das Spiel, und der Name der Klasse

Ein Feld aus vier mal vier Plättchen. Jeder Zug schiebt alle Plättchen so weit, wie
sie in eine Richtung kommen. Zwei gleiche Zahlen, die aufeinandertreffen,
verschmelzen zu einem Plättchen mit dem doppelten Wert. Nach jedem Zug, der etwas
verändert hat, erscheint ein neues Plättchen auf einem freien Feld.

Fang die Datei an. Sie kann nicht `2048.java` heißen, denn ein Java-Name darf nicht
mit einer Ziffer beginnen. Die Klasse heißt also `Game2048` und die Datei
`Game2048.java`:

```java
import java.util.Scanner;

public class Game2048 {

    static final int SIZE = 4;

    public static void main(String[] args) {
    }
}
```

`static final int SIZE = 4;` steht innerhalb der Klasse und außerhalb jeder
Methode. Das ist neu: Kurs 1 zeigt `final` nur an einer Variablen **in** einer
Methode, wo sie mit der Methode endet. Hier gehört die Zahl der Klasse, und jede
Methode kommt an sie heran — genau das brauchst du gleich, denn `draw`, `move` und
`spawn` alle verwenden sie.

## 🟢 Kern — Zweidimensionale Arrays, kurz erklärt

*(Wenn du Kurs 2 oder Kurs 4 gemacht hast, überspring das und lies beim nächsten
Abschnitt weiter.)*

Kurs 1 hat dir ein Array gegeben: eine Reihe von Werten unter einem Namen. Ein
Spielfeld ist ein Array, dessen Werte selbst Arrays sind:

```java
int[][] board = new int[SIZE][SIZE];
```

`board[1][2]` ist Zeile 1, Spalte 2, und beide zählen ab 0. Der Typ ist `int`, weil
ein Feld eine Zahl enthält, und ein frisches `int`-Array ist voller Nullen. Die 0
kann also ohne jede Vorbereitung für „leer" stehen.

Das ganze Feld durchläuft man mit einer Schleife in einer Schleife:

```java
for (int row = 0; row < SIZE; row++) {
    for (int col = 0; col < SIZE; col++) {
        // board[row][col]
    }
}
```

Noch etwas, das dieses Kapitel benutzt: `board[row]` allein, ohne zweites
Klammerpaar, ist die ganze Zeile, und sie ist ein `int[]`. Ein Spielfeld ist in
Wahrheit ein Array aus Zeilen, einer Methode, die mit einer Zeile arbeitet, kannst
du `board[2]` also direkt übergeben.

Es geht auch andersherum, und beide Schlüsselstellen dieses Kapitels hängen daran:
`board[row] = eineAndereZeile` ersetzt diese ganze Zeile auf einen Schlag. Kurs 1
hat gesagt, dass eine Array-Variable den Ort ihrer Werte hält und nicht die Werte
selbst, und hier tut diese Tatsache etwas Nützliches.

## 🟢 Kern — Ein Spielfeld im Fenster, dessen Zahlen wachsen

*(Kurs 4 zeigt dasselbe Fenster. Wer von dort kommt, kann bis zum nächsten
Abschnitt springen.)*

Ein Fenster kostet hier sieben Zeilen und keine eigene Klasse. Nichts wird
überschrieben, niemand horcht auf etwas; das kommt erst in Kurs 6 dazu, und zwar
wegen der Tastatur und nicht wegen der Anzeige.

Gebraucht werden drei Dinge: ein `BufferedImage` als Bild im Arbeitsspeicher, auf
das du malst, ein `JLabel`, dem man ein Bild geben kann, und ein `JFrame` als
Rahmen darum.

```java
import java.awt.Color;
import java.awt.Font;
import java.awt.FontMetrics;
import java.awt.Graphics;
import java.awt.image.BufferedImage;
import javax.swing.ImageIcon;
import javax.swing.JFrame;
import javax.swing.JLabel;
```

Zuerst die Maße und die Farben, zu den anderen Konstanten oben in die Klasse. Die
Fensterzeilen weiter unten benutzen `BOARD`, also muss es vorher dastehen:

```java
static final int TILE = 90;
static final int GAP = 8;
static final int BOARD = SIZE * TILE + (SIZE + 1) * GAP;

static final Color BACKDROP = new Color(187, 173, 160);
static final Color EMPTY = new Color(205, 193, 180);
static final Color DARK_TEXT = new Color(119, 110, 101);
```

Vier Plättchen zu 90 Pixeln und fünf Lücken zu 8 ergeben 400. `BOARD` rechnet sich
aus den anderen beiden aus, statt die 400 ein zweites Mal irgendwo hinzuschreiben:
Setz `TILE` auf 60, und Fenster, Plättchen und Abstände stimmen weiterhin zusammen.

`new Color(187, 173, 160)` sind Rot, Grün und Blau von 0 bis 255. Das ist das erste
Mal in diesem Kurs, dass `new` einen Typ erzeugt, der kein Array ist; mehr steckt
nicht dahinter, als dass die Klasse `Color` drei Zahlen entgegennimmt und ein
Farbobjekt daraus macht.

Jetzt das Fenster, acht Zeilen in `main`:

```java
BufferedImage picture = new BufferedImage(BOARD, BOARD, BufferedImage.TYPE_INT_RGB);
JLabel label = new JLabel(new ImageIcon(picture));
JFrame window = new JFrame("2048");
window.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
window.add(label);
window.pack();
window.setLocationRelativeTo(null);
window.setVisible(true);
```

Zeile für Zeile, weil hier sechs Namen auf einmal auftauchen:

`new BufferedImage(breite, hoehe, TYPE_INT_RGB)` legt ein Bild dieser Größe an.
`TYPE_INT_RGB` ist eine Konstante der Klasse und heißt „pro Bildpunkt Rot, Grün und
Blau, keine Durchsichtigkeit". Für ein Spielfeld ist das die richtige Wahl.

Ein `JLabel` zeigt entweder Text oder ein Bild. Ein `BufferedImage` nimmt es aber
nicht direkt; dazwischen gehört ein `ImageIcon`, das nichts weiter tut, als ein Bild
in die Form zu bringen, die Swing erwartet. Darum die Verschachtelung.

`setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE)` sagt, was das Schließkreuz tun
soll: das ganze Programm beenden. Ohne diese Zeile verschwindet nur das Fenster und
das Programm läuft weiter — merk dir das, es kommt weiter unten noch einmal, und
dort kostet es dich sonst eine Viertelstunde.

`add` setzt das Label ins Fenster, `pack()` legt das Fenster um seinen Inhalt herum
statt dich die Fenstergröße raten zu lassen, `setLocationRelativeTo(null)` setzt es
mittig auf den Bildschirm, und `setVisible(true)` zeigt es an. Vor dieser letzten
Zeile sieht man nichts.

Gezeichnet wird mit `Graphics`, das du aus dem Bild holst:

```java
static void draw(BufferedImage picture, int[][] board) {
    Graphics g = picture.createGraphics();

    g.setColor(BACKDROP);
    g.fillRect(0, 0, BOARD, BOARD);

    for (int row = 0; row < SIZE; row++) {
        for (int col = 0; col < SIZE; col++) {
            int x = GAP + col * (TILE + GAP);
            int y = GAP + row * (TILE + GAP);
            int value = board[row][col];

            g.setColor(value == 0 ? EMPTY : tileColor(value));
            g.fillRect(x, y, TILE, TILE);

            if (value != 0) {
                drawNumber(g, value, x, y);
            }
        }
    }
}
```

Aus Zeile und Spalte werden Pixel über `GAP + col * (TILE + GAP)`: eine Lücke am
Rand, dann je Plättchen seine Breite plus die Lücke dahinter.

Ganz am Ende von `draw` gehört noch eine Zeile hin:

```java
g.dispose();
```

`createGraphics()` gibt dir jedes Mal ein neues Werkzeug heraus, und `dispose()`
gibt es zurück. Bei einem Bild ist das folgenlos, bei ein paar hundert Zügen nicht
mehr. Eine Zeile, und du musst nicht wissen, ab wann es weh tut.

Die Farbe hängt am Wert. Das trifft ein `switch`, aber anders, als Kurs 1 es
gezeigt hat: Dort war `switch` eine **Anweisung**, hier ist es ein **Wert**, der
hinter `return` steht. Jeder Zweig liefert etwas, und das Ganze ergibt zusammen das
Ergebnis der Methode — deshalb steht am Ende ein Semikolon hinter der schließenden
Klammer, was bei einer Anweisung falsch wäre:

```java
static Color tileColor(int value) {
    return switch (value) {
        case 2 -> new Color(238, 228, 218);
        case 4 -> new Color(237, 224, 200);
        case 8 -> new Color(242, 177, 121);
        case 16 -> new Color(245, 149, 99);
        case 32 -> new Color(246, 124, 95);
        case 64 -> new Color(246, 94, 59);
        default -> new Color(237, 194, 46);
    };
}
```

Blass für kleine Plättchen, heiß für große. Das ist kein Schmuck: Du siehst damit,
wie weit du bist, ohne eine einzige Zahl zu lesen.

Das Problem der festen Spaltenbreite, das eine Textausgabe hätte, hat ein Fenster
nicht. Dafür hat es ein eigenes: Eine `1024` ist mehr als doppelt so breit wie eine
`2` und läuft bei fester Schriftgröße über den Rand. Also schrumpft die Schrift mit
der Stellenzahl, und die Zahl wird auf ihrem Plättchen zentriert:

```java
static void drawNumber(Graphics g, int value, int x, int y) {
    String text = String.valueOf(value);

    int size = switch (text.length()) {
        case 1, 2 -> 38;
        case 3 -> 32;
        default -> 26;
    };

    g.setFont(new Font("SansSerif", Font.BOLD, size));
    g.setColor(value <= 4 ? DARK_TEXT : Color.WHITE);

    FontMetrics metrics = g.getFontMetrics();
    int textX = x + (TILE - metrics.stringWidth(text)) / 2;
    int textY = y + (TILE + metrics.getAscent() - metrics.getDescent()) / 2;
    g.drawString(text, textX, textY);
}
```

Drei Kleinigkeiten in diesem Stück sind neu. `String.valueOf(value)` macht aus einer
Zahl Text; `"" + value` aus Kurs 1 täte dasselbe und liest sich nur schlechter.
`case 1, 2 ->` fasst zwei Fälle zu einem Zweig zusammen, was mit Pfeil-`switch`
erlaubt ist. Und `new Font("SansSerif", Font.BOLD, size)` sind Schriftname, Stil
(`Font.PLAIN`, `Font.BOLD`, `Font.ITALIC`) und Größe in Punkt.

`FontMetrics` beantwortet Fragen über die gerade eingestellte Schrift.
`stringWidth` ist die Breite dieses Textes in Pixeln; die Hälfte des übrigen Platzes
links davon zentriert ihn waagerecht.

Senkrecht ist es kniffliger, weil `drawString` die **Grundlinie** setzt und nicht
die Oberkante. `getAscent` ist, wie weit die Schrift über die Grundlinie reicht,
`getDescent`, wie weit darunter.

Setz probehalber `textY = y + TILE / 2`, also die Grundlinie genau auf die Mitte.
Die Zahlen sitzen dann sichtbar **zu hoch**. Nachgemessen auf einem 90er-Plättchen
bei Schriftgröße 38: Die Tinte liegt zwischen y=18 und y=44, ihre Mitte also bei
31 statt bei 45 — vierzehn Pixel daneben, und das sieht man sofort.

Die Formel oben schiebt die Grundlinie um die halbe Differenz von Anstieg und
Unterlänge nach unten. Damit liegt die Tinte zwischen y=33 und y=59, Mitte 46 statt
45: **ein Pixel zu tief**, und das sieht niemand.

Genau ist sie trotzdem nicht, und der Grund ist lehrreich. Sie zentriert nicht die
Ziffer, sondern den Platz, den die Schrift beanspruchen *könnte* — Anstieg 39 plus
Unterlänge 9. Eine Ziffer nutzt davon weder die Unterlänge noch den vollen Anstieg;
gemessen ist sie 27 Pixel hoch und nicht 39. Zwei Ungenauigkeiten, die sich fast
aufheben. Wen das eine Pixel stört, der misst mit
`metrics.getStringBounds(text, g)` die tatsächliche Ausdehnung dieses Textes.

Und eine Zeile, die gern vergessen wird:

```java
label.repaint();
```

In das Bild zu malen ändert nichts am Bildschirm. Erst `repaint()` holt es dorthin.
Also: erst zeichnen, dann `repaint`, dann nach dem Zug fragen.

Ein neues Plättchen kommt auf ein zufälliges freies Feld und ist meistens eine 2:

```java
static void spawn(int[][] board) {
    while (true) {
        int row = (int) (Math.random() * SIZE);
        int col = (int) (Math.random() * SIZE);
        if (board[row][col] == 0) {
            board[row][col] = Math.random() < 0.9 ? 2 : 4;
            return;
        }
    }
}
```

So lange zu würfeln, bis man ein freies Feld trifft, geht in Ordnung, solange das
Feld überwiegend leer ist, und auf einem vollen Feld wird diese Methode nie
aufgerufen.

Leg zwei Plättchen hin und gib das Feld aus:

```java
int[][] board = new int[SIZE][SIZE];
spawn(board);
spawn(board);

draw(picture, board);
label.repaint();
```

## 🟢 Kern — Einen Zug tippen, und die Enter-Taste im Weg

Im echten Spiel drückst du eine Pfeiltaste und das Feld bewegt sich sofort. Hier
tippst du einen Buchstaben und drückst Enter, und das ist keine Abkürzung. Java
kann aus einem Terminal überhaupt keinen einzelnen Tastendruck lesen. Das Terminal
sammelt erst eine ganze Zeile, bevor es irgendetwas herausgibt, und das JDK hat
keine Möglichkeit, es darum zu bitten, das zu lassen. Pfeiltasten sind noch
schlimmer: Sie kommen als mehrere Zeichen auf einmal an.

Also: `w`, `a`, `s`, `d`, und `q` zum Beenden, jeweils gefolgt von Enter.

```java
Scanner in = new Scanner(System.in);

System.out.print("Move (w/a/s/d, q to quit): ");
String line = in.nextLine().trim().toLowerCase();
```

`.toLowerCase()` sorgt dafür, dass ein versehentliches großes `W` trotzdem geht,
und `.trim()` verzeiht ein Leerzeichen.

Behandle die Beenden-Taste vor allem anderen, denn sie ist keine Richtung und hat
in der Richtungszuordnung nichts verloren:

```java
if ("q".equals(line)) {
    System.out.println("Bye.");
    System.exit(0);
}
```

Dort steht `System.exit(0)` und nicht `return`, und das ist die unangenehmste
Überraschung dieses Kapitels. Solange ein Fenster offen ist, hält Swing einen
eigenen Thread am Leben, und der ist kein Hintergrund-Thread. Aus `main`
zurückzukehren beendet das Programm deshalb **nicht**: Die Ausgabe `Bye.`
erscheint, der Prompt kommt nie zurück, und das Terminal hängt, bis du es
abwürgst. Probier es ruhig mit `return` aus, damit du das Verhalten einmal gesehen
hast; wer es nicht kennt, sucht den Fehler bei sich.

`System.exit(0)` beendet die ganze JVM sofort. Die Null heißt „ohne Fehler". Nach
dem Spielende weiter unten gilt dasselbe. Die dritte Möglichkeit ist das
Schließkreuz am Fenster, und die funktioniert nur, weil weiter oben
`setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE)` steht.

Das Spielfeld sieht jetzt aus wie ein Spiel, und gesteuert wird es trotzdem mit
Enter. Genau dieser Widerspruch ist die Grenze, der die Kurse 6 und 7 entkommen,
indem das Fenster die Taste selbst entgegennimmt statt nur zu zeigen. Es lohnt sich
zu wissen, welche von beiden die echte Einschränkung ist: das Terminal, nicht Javas
Fähigkeit, Spiele zu bauen.

## 🟢 Kernübung — Eine Zeile schieben

Alles in diesem Spiel passiert mit einer einzelnen Zeile, nach links geschoben.
Bekomm das richtig hin, und der Rest ist Buchhaltung.

```java
static int[] slideRowLeft(int[] row) {
    // dein Code hier -- die drei Schritte unten
}
```

1. **Zusammenschieben.** Lauf durch die Zeile und kopier jeden Wert ungleich 0 in
   ein neues Array, einen nach dem anderen ab Stelle 0. Lücken verschwinden, die
   Reihenfolge bleibt.
2. **Verschmelzen.** Lauf von links nach rechts durch das zusammengeschobene
   Array, und hör ein Feld vor dem Ende auf, denn jeder Schritt schaut auch auf
   den Wert daneben. Wo ein Wert nicht 0 und gleich seinem Nachbarn ist, verdopple
   den ersten und setz den zweiten auf 0.
3. **Nochmal zusammenschieben.** Das Verschmelzen hinterlässt Löcher, also mach
   Schritt 1 ein zweites Mal und gib das Ergebnis zurück.

Schritt 2 hört bei `SIZE - 1` auf und nicht bei `SIZE`. Die Schleife liest
`packed[i + 1]`, bis ganz ans Ende zu laufen greift also eine Stelle hinter das
Array.

Was dann passiert, hängt vom Inhalt ab, und das macht den Fehler gemein. Mit
`2 4 2 4` knallt es sofort:
`ArrayIndexOutOfBoundsException: Index 4 out of bounds for length 4`. Mit
`2 2 2 2` — der ersten Testzeile gleich hier unten — knallt es **nicht**, weil
`packed[i] != 0` links vom `&&` steht und bei der letzten Stelle schon falsch ist,
sodass `packed[4]` nie gelesen wird. Das Ergebnis ist dann still `4 . 4 .` statt
`4 4 . .`.

Ein Fehler, der mal abstürzt und mal ein falsches Ergebnis liefert, ist schlimmer
als einer, der immer abstürzt. Deshalb die Grenze von vornherein richtig setzen,
statt sich darauf zu verlassen, dass es schon auffällt.

Ein Plättchen darf pro Zug höchstens einmal verschmelzen, und in dieser Fassung
sorgt der Test auf 0 dafür: Ein verschmolzener Partner wird 0, der nächste Schritt
kann ihn also nicht noch einmal aufgreifen. Das ist wissenswert, weil man leicht
annimmt, es brauche zusätzliche Buchführung, und sie dann schreibt.

Rechne diese Fälle auf Papier durch, bevor du irgendetwas schreibst:

```
2 2 2 2   wird   4 4 . .      (zwei getrennte Verschmelzungen, keine 8)
4 2 2 .   wird   4 4 . .      (die beiden 2 verschmelzen, die 4 bleibt)
2 2 4 .   wird   4 4 . .      (dasselbe Ergebnis, anderer Grund)
4 4 4 4   wird   8 8 . .
2 4 2 4   wird   2 4 2 4      (nichts verschmilzt, nichts bewegt sich)
```

Die dritte Zeile entscheidet, ob deine Fassung stimmt, und der Grund lohnt sich
frontal.

Drei Schritte mit einem eigenen Zwischenarray sehen nach mehr Arbeit aus als nötig,
und die verlockende Abkürzung ist, das Ergebnis in einem Durchgang aufzubauen: eine
Schreibstelle mitführen und für jeden ankommenden Wert entweder ein neues Plättchen
beginnen oder das gerade geschriebene verdoppeln. Das ist kürzer und es ist falsch.
Bei `2 2 4 .` verschmilzt es die beiden 2 zu einer 4, trifft dann die vorhandene 4
neben der soeben geschriebenen 4, und verschmilzt noch einmal: `8 . . .`. Das
Plättchen, das in diesem Zug entstanden ist, verschmilzt im selben Zug ein zweites
Mal.

Zusammenschieben, verschmelzen, zusammenschieben vermeidet das, weil der
Verschmelzungsdurchlauf nur Werte ansieht, die schon da waren, als er begann. Der
Preis ist ein zusätzliches Array und ein zusätzlicher Durchlauf; der Gewinn ist
eine Regel, die sich nicht aus Versehen brechen lässt.

Teste deine Methode mit allen fünf Zeilen oben, bevor du dich ans Spielfeld machst.

## 🟢 Kern — Vier Richtungen, eine Operation

„Links" hast du jetzt. Statt drei weitere Fassungen zu schreiben, dreh das
Spielfeld und benutz die, die du hast.

```java
static void rotateClockwise(int[][] board) {
    int[][] turned = new int[SIZE][SIZE];
    for (int row = 0; row < SIZE; row++) {
        for (int col = 0; col < SIZE; col++) {
            turned[col][SIZE - 1 - row] = board[row][col];
        }
    }
    for (int row = 0; row < SIZE; row++) {
        board[row] = turned[row];
    }
}
```

Das Feld an `(row, col)` landet bei `(col, SIZE - 1 - row)`. Nimm ein Blatt Papier
mit einem Buchstaben in jeder Ecke und dreh es eine Vierteldrehung, um dich davon
zu überzeugen.

Die letzte Schleife kopiert die Zeilen zurück in das Spielfeld, das übergeben
wurde, damit der Aufrufer die Änderung sieht. `board = turned` würde nur den
lokalen Namen auf das neue Feld richten und draußen nichts ändern, und das ist die
Grenze dessen, was „Arrays sind Verweise" dir kauft.

Ein Zug ist dann: drehen, jede Zeile nach links schieben, zurückdrehen.

```java
static void move(int[][] board, int rotations) {
    for (int i = 0; i < rotations; i++) {
        rotateClockwise(board);
    }

    for (int row = 0; row < SIZE; row++) {
        board[row] = slideRowLeft(board[row]);
    }

    for (int i = 0; i < (4 - rotations) % 4; i++) {
        rotateClockwise(board);
    }
}
```

Wie viele Drehungen zu welcher Richtung gehören, leitet man besser her, als es
auswendig zu lernen. Hier ist die Antwort zum Gegenprüfen: links ist 0, runter ist
1, rechts ist 2, hoch ist 3. Teste jede Richtung mit einem einzelnen Plättchen in
einer bekannten Ecke und schau, wo es landet.

Das `switch` aus Kurs 1 macht aus einem Buchstaben diese Zahl:

```java
int rotations = switch (line) {
    case "a" -> 0;
    case "s" -> 1;
    case "d" -> 2;
    case "w" -> 3;
    default -> -1;
};

if (rotations < 0) {
    System.out.println("Type w, a, s or d, or q to quit.");
    continue;
}
```

Das ist ein `switch`, das als Wert benutzt wird und nicht als Anweisung: Das Ganze
ergibt eine Zahl, und deshalb steht am Ende ein Semikolon. Die `-1` steht für
„keine Richtung", so wie Kurs 2 die 0 für „kein Feld" benutzt hat.

## 🟢 Kern — Ein Zug, der nichts verändert

Schieb zweimal nach links, und das zweite Mal passiert nichts. Erscheint trotzdem
ein neues Plättchen, bekommt der Spieler Gratisplättchen für einen Tastendruck,
der nichts bewegt hat, und das Feld füllt sich, ohne dass gespielt wurde.

Also vergleich vorher und nachher:

```java
int[][] before = copy(board);
move(board, rotations);

if (same(before, board)) {
    System.out.println("Nothing moves that way.");
    continue;
}

spawn(board);
```

`copy` und `same` sind beide eine Schleife in einer Schleife, eine schreibend und
eine vergleichend:

```java
static int[][] copy(int[][] board) {
    int[][] result = new int[SIZE][SIZE];
    for (int row = 0; row < SIZE; row++) {
        for (int col = 0; col < SIZE; col++) {
            result[row][col] = board[row][col];
        }
    }
    return result;
}
```

Warum nicht `int[][] before = board;`? Weil das ein Spielfeld mit zwei Namen ist,
und nach dem Zug zeigen beide Namen auf das bewegte Feld. Der Vergleich sagt dann
immer „nichts geändert", es erscheint also nie ein Plättchen, und das Spiel meldet
nach jedem einzelnen Zug „Nothing moves that way.", während sich das Feld sichtbar
bewegt. Kurs 1 hat genau davor unter „Arrays sind Verweise" gewarnt, und das hier
ist die Stelle, an der das Vergessen ein Spiel erzeugt, das kaputt aussieht, ohne
dass der Code erklärt warum.

`same` schreibst du selbst; es ist `copy` mit einem Vergleich statt einer Zuweisung
und einem frühen `return false`.

Jetzt die Schleife in `main`. Sie ist das Stück, in dem alles zusammenkommt, und
deshalb steht ihr Gerüst hier:

```java
while (true) {
    draw(picture, board);
    label.repaint();

    System.out.print("Move (w/a/s/d, q to quit): ");
    String line = in.nextLine().trim().toLowerCase();

    // dein Code hier -- q behandeln, Richtung bestimmen, ungueltige Eingabe
    // abweisen, Feld kopieren, ziehen, mit der Kopie vergleichen

    spawn(board);

    if (isFull(board)) {
        draw(picture, board);
        label.repaint();
        System.out.println("Board full. Game over.");
        System.exit(0);
    }
}
```

Die Reihenfolge ist nicht beliebig. Gezeichnet wird **vor** der Frage nach dem Zug,
sonst siehst du immer das Feld von vorletztem Mal. Und `spawn` kommt erst nach dem
Vergleich, denn ein Zug, der nichts verändert hat, darf kein Plättchen schenken.

`isFull` fehlt dir noch: eine Doppelschleife, die `false` liefert, sobald sie eine 0
findet, und sonst `true`. Drei Zeilen, nach demselben Muster wie `same`.

Auch hier `System.exit(0)` statt `return`, aus demselben Grund wie bei `q`.

## 🟡 Optional — Ein Punktestand

Zähl den Wert jeder Verschmelzung zusammen und zeig die Summe. Verschmolzen wird
nur in `slideRowLeft`, und die gibt eine Zeile zurück und hat damit keinen Platz
für eine zweite Antwort.

Der naheliegende Weg braucht etwas, das Kurs 1 nicht gezeigt hat: eine Variable,
die in der Klasse lebt statt in einer Methode, damit `slideRowLeft` und `main`
beide an sie herankommen.

```java
static int score;
```

Anders als `SIZE` ist sie nicht `final`, denn sie ändert sich. Zähl dort dazu, wo
verschmolzen wird, gib sie neben dem Feld aus, und setz sie zurück, wo ein neues
Spiel beginnt.

Eine Wechselwirkung, auf die du achten musst, wenn du auch die rote Herausforderung
unten machst: Eine Spielende-Prüfung, die alle vier Züge probeweise ausführt, um zu
sehen ob einer etwas bewegt, würde `slideRowLeft` je Probe laufen lassen und den
Punktestand aufblähen. Die Nachbarprüfung in jenem Abschnitt umgeht das, weil sie
nichts bewegt, und das ist ein weiterer Grund, sie vorzuziehen.

## 🟡 Optional — Mehrere Züge in einer Zeile

Ein Zug pro Enter ist mühsam. Nimm `wasd` als vier Züge in einer Zeile an, indem du
mit `charAt` aus Kurs 1 über die Zeichen läufst und jedes als eigenen Zug
behandelst.

Achte auf das Detail, das dabei sichtbar wird: Nach jedem Buchstaben musst du
prüfen, ob sich das Feld verändert hat und ob ein neues Plättchen kommt, genau wie
in der Fassung mit einem Zug.

## 🔴 Optional, echte Herausforderung — Richtiges Spielende

Die grüne Fassung endet, wenn das Feld voll ist. Das ist nicht die echte Regel. Ein
volles Feld ist weiter spielbar, solange zwei gleiche Plättchen nebeneinander
liegen, denn dieser Zug verschmilzt sie und macht ein Feld frei.

Schreib die echte Prüfung: Das Spiel ist vorbei, wenn es kein leeres Feld gibt
**und** keine zwei waagerecht oder senkrecht benachbarten Plättchen gleich sind.

```java
static boolean isGameOver(int[][] board) {
    // dein Code hier -- kein leeres Feld, und keine gleichen Nachbarn
}
```

Jedes Feld mit dem rechts daneben und dem darunter zu vergleichen genügt, um jedes
Nachbarpaar genau einmal zu erfassen. Überleg dir, warum links und oben zusätzlich
zu prüfen verschwendete Mühe wäre.

Dann die zweite Hälfte, der man schwerer widersteht falsch zu machen: Ein
Plättchen, das in eine Richtung frei verschmelzen kann, ist in einer anderen
vielleicht blockiert. Überzeug dich davon, dass die Nachbarprüfung oben sich für
die Richtung nicht interessiert, und dass das richtig so ist.

Bau zum Testen absichtlich ein volles Feld, indem du das Array in `main` von Hand
füllst, bevor die Schleife startet.
